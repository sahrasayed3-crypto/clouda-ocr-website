Where we are now

What already exists — and what is still blocked

The project is asking for support at a specific technical stage — not from a standing start. What exists, what is blocked, and what persistent local compute makes possible.

What already exists

Built
  • Open-source codebase — a working, public codebase for the OCR and Document AI pipeline.
  • Completed 177-page benchmark — controlled Arabic OCR benchmark with per-model outputs, Arabic-specific scoring and public audit records.
  • Leading candidate identified — benchmark results point to a current leading candidate for validation.
  • Data & training infrastructure — data-preparation, evaluation, training-planning, preflight and checkpoint/resume tooling has been developed, with newer training components currently awaiting final integration review.
  • Source material identified — sufficient material to proceed with the current phase. Actual training use remains subject to licensing, provenance, and holdout protections.
  • Measurable roadmap — expand benchmark, adapt the selected model, evaluate, iterate.

What is still blocked

Blocked
  • Real VRAM usage — actual GPU memory requirements need hardware validation.
  • Mixed-precision behavior — BF16/FP16 mixed-precision behavior must be measured on real hardware, not assumed.
  • Throughput ceilings — batch-size limits and training throughput require real hardware.
  • Checkpoint behavior — save/load sizes, resume reliability, and OOM recovery need real-GPU testing.
  • Large-scale training — full model adaptation and pilot training do not run on the current machine.

Why local compute: repeatability, persistent access, restricted-data handling, lower iteration friction. Cloud remains useful for bursts that exceed local capacity.

Transparency

What still requires hardware validation

The project does not claim a final trained model, validated production accuracy, or completed GPU training. These are the open items this phase is designed to answer with measurements:

Real training runsActual training with the selected model weights on real GPU hardware.
VRAM requirementsMeasured memory use, including BF16/FP16 mixed-precision behavior.
Throughput ceilingsMeasured speed and batch-size limits under real conditions.
Checkpoint behaviorCheckpoint sizes, save/load behavior and GPU OOM recovery.
Multi-GPU scalingOnly if multi-GPU hardware is later used.
Measured quality gainActual quality improvement after adaptation, evaluated on held-out data.

Spending flexibility: actual spending may shift between categories as hardware prices, measured bottlenecks, and project needs change, while remaining within the same current-phase technical purpose. Cash support and infrastructure support are tracked separately so the project does not overstate what one funding source covers.
