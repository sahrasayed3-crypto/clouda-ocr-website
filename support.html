Why local compute now

Validation needs repetition, not one-off access

Hardware-validation work is inherently iterative, and cloud access alone does not fit that pattern.

Repeatability

The same run must be repeated many times to measure memory, throughput, precision behavior and failure recovery.

Persistent access

Development continues on the project's own schedule rather than inside expiring credit windows.

Restricted data

Some licensed or restricted material can only be processed under local handling terms.

Lower iteration friction

Small diagnostic runs and config changes are cheap locally; every step does not need a cloud job.

Cloud for bursts

Cloud capacity is reserved for workloads that genuinely exceed local hardware. Local is chosen for control and persistence, not assumed to be cheaper.

Transparency

What still requires hardware validation

The project does not claim a final trained model, validated production accuracy, or completed GPU training. These are the open items this phase is designed to answer with measurements:

Real training runs Actual training with the selected model weights on real GPU hardware.
VRAM requirements Measured memory use, including BF16/FP16 mixed-precision behavior.
Throughput ceilings Measured speed and batch-size limits under real conditions.
Checkpoint behavior Checkpoint sizes, save/load behavior and GPU OOM recovery.
Multi-GPU scaling Only if multi-GPU hardware is later used.
Measured quality gain Actual quality improvement after adaptation, evaluated on held-out data.

Spending flexibility: actual spending may shift between categories as hardware prices, measured bottlenecks, and project needs change, while remaining within the same current-phase technical purpose. Cash support and infrastructure support are tracked separately so the project does not overstate what one funding source covers.
